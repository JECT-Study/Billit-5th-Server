# 이슈와 PR 작성 지침

브랜치, 커밋, 검토와 병합 절차는 [Git 작업 규칙](git-workflow.md)을 따릅니다.

## 공통 규칙

- 기존 기획, 이슈와 가이드는 링크하고, 이번 작업에서 결정하거나 변경할 내용만 적습니다.
- diff에서 확인할 수 있는 파일 목록, 코드와 구현 순서는 반복하지 않습니다.
- 임시 코드 분리, worktree 이동 등 내부 작업 과정과 사용자에게 설명할 사정은 본문에 넣지 않습니다.
- 같은 내용을 여러 항목에 반복하지 않습니다.
- 특정 파일의 변경이나 검토 위치를 짚을 때는 `파일명`: 설명 형식을 사용합니다. 파일명이 같으면 구분할 수 있는 경로를 적습니다.
- 파일별 수정 목록으로 변경 목적과 결과를 대신하지 않습니다.
- 템플릿 항목은 유지하고 해당하지 않는 항목에는 이유를 짧게 적습니다.
- 템플릿에는 특정 라벨을 고정하지 않습니다.
- 익숙한 기술 용어는 유지하되, 뜻이 모호한 표현 대신 대상과 동작을 구체적으로 적습니다. 예를 들어 `호출부` 대신 `이 API를 사용하는 코드`로 적습니다.

## 이슈 작성

일반 작업은 [일반 작업 이슈 템플릿](../../.github/ISSUE_TEMPLATE/task.yml), 버그 제보는 [버그 이슈 템플릿](../../.github/ISSUE_TEMPLATE/bug.yml)을 사용합니다.

- 작업 배경, 범위와 완료 기준을 적습니다. 완료 기준은 확인할 수 있는 동작이나 결과로 작성합니다.
- 구현 세부사항은 작업 범위나 판단에 영향을 줄 때만 상세 내용에 적습니다. 완료 기준은 구현 방식보다 확인할 동작과 결과를 중심으로 작성합니다.
- 동시에 나누어 작업하거나 따로 완료할 수 있을 때만 하위 이슈를 만듭니다. 하나의 이슈를 여러 PR로 나눌 수 있습니다.
- 상위 이슈에는 전체 목표와 완료 기준을, 하위 이슈에는 독립적으로 끝낼 범위와 완료 기준, 상위 이슈 번호를 적습니다.
- 버그 제보에는 현상, 재현 방법, 기대 동작과 실제 동작을 적습니다. 재현 조건을 모르면 확인한 발생 상황을 적습니다.

## PR 생성 전 확인

- 이슈와 작업 범위가 달라지거나 필요한 검증이 실패하거나 실행되지 않았다면, PR 생성 전에 사용자에게 보고하고 진행 여부를 확인받습니다.
- 보고에는 차이 또는 실패 내용, 영향과 제안하는 처리 방향을 포함합니다.
- PR 본문에 사유를 적거나 Draft로 생성하는 것으로 사용자 확인을 대신하지 않습니다.
- 생성이 승인된 뒤에도 리뷰와 병합 판단에 영향을 주는 검증 제한은 본문에 간결하게 남깁니다.

## PR 작성

[PR 템플릿](../../.github/pull_request_template.md)을 사용합니다.

| 항목 | 작성 내용 |
| --- | --- |
| 관련 이슈 | 중간 PR은 `related #번호`, 이슈를 완료하는 PR은 `Closes #번호`를 적습니다. 하위 이슈 작업이면 상위 이슈도 연결합니다. |
| 작업 내용 | 변경 목적, 핵심 결과와 이번 PR의 구현 범위를 적습니다. 동작이 달라지면 변경 전후 차이를 설명합니다. |
| 리뷰 포인트 | 확인받을 부분과 구현 방식을 선택한 이유를 적습니다. 가이드를 따르지 않았다면 이유를 설명합니다. API, DB, 환경변수가 바뀌어 기존 코드나 설정을 그대로 사용할 수 없다면 영향과 배포 순서를 적습니다. |
| 검증 결과 | 실행한 검증과 결과, 실행하지 못한 검증과 이유, 남은 위험과 병합 후 확인할 사항을 적습니다. |

### 작성 분량

- 오탈자, 서식과 이름만 바꾸는 PR은 작업 내용을 한두 문장으로 작성합니다.
- 여러 구현 방식을 비교했거나 가이드를 따르지 않았다면 선택 이유를 리뷰 포인트에 적습니다.
- 리뷰 포인트에는 리뷰어의 판단이 필요한 결정과 호환성, 배포 영향을 적습니다. 구현 설명을 반복하지 않습니다.
- 검증 결과는 검사 이름과 결과로 요약합니다. 재현에 필요하지 않으면 전체 명령어, 실행 환경과 로그를 나열하지 않습니다. 실패 원인이나 성능 차이의 근거가 되는 부분만 첨부합니다.

## 작성 예시

아래 이슈 번호, 기능과 검증 결과는 작성 형식을 보여주는 가상 예시입니다.

### 일반 작업 이슈

```markdown
### 작업 배경

목록 조회 API가 모든 데이터를 한 번에 반환합니다.

### 작업 범위

목록 조회 API에 페이지 조회를 추가합니다. 목록의 정렬 기준은 변경하지 않습니다.

### 완료 기준

- 요청한 페이지에 해당하는 데이터만 반환합니다.
- 마지막 페이지 이후에는 빈 목록을 반환합니다.
- 페이지 번호가 허용 범위를 벗어나면 입력 오류로 응답합니다.
```

### 기능 변경 PR

```markdown
## 관련 이슈

Closes #123

## 작업 내용

- 목록 조회 API가 전체 데이터 대신 요청한 페이지의 데이터를 반환하도록 변경했습니다.

## 리뷰 포인트

- 응답 형식이 변경되므로 클라이언트 수정과 배포 순서를 맞춰야 합니다. 기존 응답 형식을 사용하는 코드가 남아 있는지 확인해주세요.

## 검증 결과

- 페이지 조회, 마지막 페이지 이후 조회와 잘못된 페이지 번호 테스트 통과
- 클라이언트 연동은 확인하지 못했습니다. 배포 전 통합 환경에서 변경된 응답 처리를 확인해야 합니다.
```

### 문서 수정 PR

```markdown
## 관련 이슈

Closes #124

## 작업 내용

- 개발 환경 실행 안내의 잘못된 문서 링크를 수정했습니다.
- `README.md`: 실행 안내에서 참조하는 설정 문서 경로 수정

## 리뷰 포인트

- 없음. 링크 대상만 수정했습니다.

## 검증 결과

- 상대 경로가 가리키는 파일의 존재 확인
- 실행 코드 변경이 없어 테스트는 실행하지 않았습니다.
```
