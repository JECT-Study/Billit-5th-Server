# 이슈와 PR 작성 지침

이슈와 PR의 단위, 제목, 섹션, 분량과 코멘트는 문서 저장소의 [Issue와 PR 작성 가이드](https://github.com/JECT-Study/Billit-5th-Docs/blob/main/guide/Issue와%20PR%20작성%20가이드.md)를 따릅니다. 이 문서는 서버 저장소에만 적용하는 규칙을 정합니다. 브랜치, 커밋, 검토와 병합 절차는 [Git 작업 규칙](git-workflow.md)을 따릅니다.

## 템플릿

| 대상 | 템플릿 |
| --- | --- |
| 작업 이슈 | [일반 작업 이슈 템플릿](../../.github/ISSUE_TEMPLATE/task.yml) |
| 버그 이슈 | [버그 이슈 템플릿](../../.github/ISSUE_TEMPLATE/bug.yml) |
| PR | [PR 템플릿](../../.github/pull_request_template.md) |

정책, API 계약과 설계에 팀의 결정이 필요하면 서버 저장소에 이슈를 만들지 않고 문서 저장소에 논의 이슈를 만듭니다. 작업 이슈의 `참고 자료`에는 그 논의 이슈를 씁니다.

## 이슈와 PR 연결

- 이슈를 완료하는 PR은 `Closes #번호`, 이슈의 일부만 처리하는 PR은 `Related #번호`를 씁니다.
- 하위 이슈를 처리하는 PR은 상위 이슈도 `Related #번호`로 씁니다.

## 변경 위치 표기

- 특정 파일의 변경이나 검토 위치를 짚을 때는 `파일명`: 설명 형식을 씁니다. 파일명이 같으면 구분할 수 있는 경로를 씁니다.
- 파일별 수정 목록으로 변경 목적과 결과를 대신하지 않습니다. 변경 위치 목록은 PR의 `세부 사항`에 씁니다.

## PR 생성 전 확인

- 이슈와 작업 범위가 달라지거나 필요한 검증이 실패하거나 실행되지 않았다면, PR 생성 전에 사용자에게 보고하고 진행 여부를 확인받습니다.
- 보고에는 차이 또는 실패 내용, 영향과 제안하는 처리 방향을 포함합니다.
- PR 본문에 사유를 적거나 Draft로 생성하는 것으로 사용자 확인을 대신하지 않습니다.
- 생성이 승인된 뒤에도 리뷰와 병합 판단에 영향을 주는 검증 제한은 `검증 결과`에 남깁니다.

## 서버 PR의 리뷰 포인트

다음 변경이 있으면 `리뷰 포인트`에 영향과 배포 순서를 씁니다.

- API의 요청, 응답이나 오류 코드
- DB 스키마와 마이그레이션
- 환경변수와 설정 값
