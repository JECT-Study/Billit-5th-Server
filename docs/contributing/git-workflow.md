# Git 작업 규칙

## 작업 흐름

1. 작업 전에 이슈를 생성합니다. 일반 작업과 버그 제보는 해당 템플릿을 사용하고, 담당자와 작업 유형 라벨을 지정합니다.
2. `develop`에서 작업 브랜치를 생성합니다. 의존 작업은 필요한 변경이 있는 브랜치에서 분기합니다. 브랜치 이름에 이슈 번호를 포함합니다.
3. 의미 있는 변경 단위로 나누어 커밋합니다.
4. 독립적인 작업은 `develop`, 의존 작업은 바로 아래 PR의 브랜치를 대상으로 PR을 생성합니다. 이슈 연결은 [PR 본문](#pr-본문)을 따릅니다.
5. 작성자 외 팀원 1명의 Approve와 필수 CI 통과 후 머지합니다.
6. 일반 작업 PR은 Squash merge하고 후속 PR이 없는 작업 브랜치를 삭제합니다.

## 브랜치

| 브랜치 | 용도 |
| --- | --- |
| `main` | 배포 버전 |
| `develop` | 개발 통합, GitHub 기본 브랜치 |
| `feat/{이슈번호}-{요약}` | 기능 개발 |
| `fix/{이슈번호}-{요약}` | 버그 수정 |
| `refactor/{이슈번호}-{요약}` | 동작 변화 없는 코드 개선 |
| `chore/{이슈번호}-{요약}` | 빌드, 패키지, 설정 |
| `docs/{이슈번호}-{요약}` | 문서 |
| `test/{이슈번호}-{요약}` | 테스트 |
| `style/{이슈번호}-{요약}` | 코드 포맷 |
| `hotfix/{이슈번호}-{요약}` | 배포 중 긴급 수정 |

- 요약은 영문 소문자와 하이픈으로 작성합니다. 예: `feat/23-expense-split-form`
- `main`, `develop`에 직접 push하지 않습니다.
- `hotfix`는 `main`에서 분기하고 `main` 대상 PR로 반영합니다. 이후 `develop`에도 같은 수정이 반영되도록 별도 PR을 생성합니다.

## 커밋 메시지

형식은 `type: 제목`으로 통일합니다.

```text
feat: 정산 미리보기 화면 추가

- 정산을 확정하기 전에 참여자별 금액을 확인하도록 미리보기 추가
```

| type | 의미 |
| --- | --- |
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 코드 개선 |
| `style` | 포맷팅 등 코드 스타일 수정. UI 변경은 `feat` 또는 `fix` 사용 |
| `chore` | 빌드, 패키지, 설정 |
| `docs` | 문서 |
| `test` | 테스트 |

- 제목 줄은 `type: `을 포함해 50자 이내로 작성합니다. 제목은 한국어로 쓰고 끝에 마침표를 붙이지 않습니다.
- 본문은 선택 사항이며 무엇을 변경했고 왜 변경했는지 작성합니다.

## 이슈 작성

- 작업 이슈에는 작업 이유, 범위와 완료 기준을 적습니다. 상세 구현 방향은 미리 확정하지 않아도 됩니다.
- 하나의 이슈는 여러 PR로 나눌 수 있습니다. 병렬로 작업하거나 따로 완료할 수 있을 때만 하위 이슈를 만듭니다.
- 상위 이슈에는 작업 배경, 목표와 완료 기준을 적습니다. 하위 이슈에는 독립적으로 끝낼 작업과 상위 이슈 번호를 적습니다.
- 버그 제보에는 현상, 재현 방법, 기대 동작과 실제 동작을 적습니다. 재현 조건을 모르면 확인한 발생 상황을 적습니다.

### 병합 후 오류

- 기존 이슈의 완료 기준을 충족하지 못했으면 기존 이슈를 재오픈하고 `fix` 작업으로 수정합니다.
- 기존 완료 기준과 직접 관련 없는 오류는 새 버그 이슈로 등록합니다.
- 배포, 외부 연동과 통합 환경에서만 확인할 수 있는 검증은 기존 이슈의 완료 기준에 포함합니다.
- 재오픈한 이슈 본문은 수정하지 않습니다. 오류 내용, 발생 환경과 후속 PR 번호는 댓글에 기록합니다.

## PR 본문

- 변경 목적, 핵심 결과와 검토 지점을 적습니다. 구현 과정과 파일 목록은 나열하지 않습니다.
- 템플릿 항목은 유지하고 해당하지 않는 항목에는 이유를 적습니다.
- 검증 결과, 실행하지 못한 검증과 사유, 남은 위험은 검증 결과 항목에 적습니다.
- 중간 PR에는 `related #번호`, 이슈를 완료하는 PR에만 `Closes #번호`를 적습니다. 하위 이슈 작업이면 상위 이슈도 연결합니다.
- 기본 브랜치가 아닌 브랜치 대상 PR은 이슈 자동 종료 여부를 별도로 확인하고, 완료 기준 충족 후 이슈를 종료합니다.
- 각 PR은 리뷰하고 검증할 수 있는 범위로 나눕니다. 기능, 리팩터링, 대규모 포맷 변경과 의존성 갱신은 가능한 한 별도 PR로 만듭니다.

다음은 PR 작업 내용과 리뷰 포인트의 작성 예시입니다.

```md
## 작업 내용

- 정산 확정 전에 참여자별 부담 금액을 확인할 수 있도록 미리보기 추가

## 리뷰 포인트

- 환율 적용 시점과 소수점 처리 결과 확인 필요
```

파일 생성과 수정 순서를 길게 나열하는 설명은 피합니다.

## 머지와 릴리스

- 일반 작업 PR과 hotfix PR은 Squash merge합니다.
- 릴리스는 `develop`에서 `main`으로 PR을 생성하고 Merge commit으로 머지한 뒤 `v0.1.0` 형식의 태그를 부여합니다.
- 릴리스 PR에도 작성자 외 1명의 Approve와 필수 CI 통과를 적용합니다.
- 후속 PR이 없는 작업 브랜치는 머지 후 삭제하고 `main`, `develop`은 유지합니다.
- 모든 리뷰 대화를 해결한 뒤 병합합니다. AI 리뷰도 포함합니다.
- 리뷰 뒤 변경 사항을 추가하면 다시 검토받습니다.

## 라벨과 템플릿

- 조직에서 미리 구성한 기존 라벨을 사용합니다. 이슈와 PR에는 작업에 해당하는 라벨을 선택합니다.
- 템플릿에는 특정 라벨을 고정하지 않습니다.
- 담당자는 Assignee로 지정하고 작업 유형은 라벨로 구분합니다.
- [일반 작업 이슈 템플릿](../../.github/ISSUE_TEMPLATE/task.yml), [버그 이슈 템플릿](../../.github/ISSUE_TEMPLATE/bug.yml), [PR 템플릿](../../.github/pull_request_template.md)을 사용합니다.
- PR에서 프로젝트가 요구하는 검사, 테스트와 빌드 결과를 확인합니다. 백엔드의 실행 명령은 [실행과 검증](../../AGENTS.md#실행과-검증)과 [CI](../../.github/workflows/ci.yml)를 따릅니다.

## GitHub 저장소 설정

- 기본 브랜치를 `develop`으로 지정합니다. `Closes #번호`를 통한 이슈 자동 종료는 기본 브랜치 대상 PR에서 동작하므로 이슈 자동 종료 설정도 활성화합니다.
- `main`, `develop`에 브랜치 보호를 적용합니다. PR, Approve 1명과 필수 CI 통과를 요구하고 직접 push와 보호 규칙 우회를 허용하지 않습니다.
- Squash merge와 Merge commit을 허용하고 Rebase merge는 비활성화합니다. Merge commit은 릴리스 PR에서만 사용합니다.
- `main`에는 릴리스 Merge commit을 허용하도록 선형 이력 필수 설정을 적용하지 않습니다.
- `Automatically delete head branches`를 활성화하고 `main`, `develop`은 보호 규칙으로 삭제를 방지합니다.

이 절은 적용해야 할 설정을 정의하며, 실제 GitHub 설정의 적용 여부는 별도로 확인합니다.
