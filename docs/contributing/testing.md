# 테스트 가이드

## 테스트 설계

테스트를 작성하기 전에 검증 대상, 실행 범위와 목적을 각각 결정합니다. 테스트는 보장하는 업무 정책, 실패 경계, 데이터 흐름과 트랜잭션 결과를 구체적인 사례로 보여줍니다.

### 검증 대상

업무 정책, 상태 전이, 계산, 불변식, 유스케이스 흐름, 트랜잭션, DB 매핑, 쿼리, 외부 API, 직렬화, HTTP 계약, 입력 검증, 인증과 오류 응답 중 검증할 대상을 정합니다.

### 실행 범위

| 범위 | 함께 실행하는 대상 |
| --- | --- |
| 단위 테스트 | 업무 정책, 계산 또는 격리할 가치가 있는 UseCase의 판단 |
| 컴포넌트 테스트 | DB 어댑터, 외부 클라이언트나 HTTP 어댑터와 해당 경계에 필요한 인프라 |
| 통합 테스트 | 유스케이스, 실제 DB, 트랜잭션과 애플리케이션 구성 요소 |
| E2E 테스트 | 실제 진입점부터 주요 인프라까지 연결된 핵심 사용자 시나리오 |

### 목적

기대 결과 검증, 회귀 방지, 실행 가능한 명세, 설계 피드백과 업무 흐름 문서화 중 테스트의 목적을 정합니다. 하나의 테스트가 여러 목적을 가질 수 있습니다. 검증 대상만으로 실행 범위를 고정하지 않습니다.

## 범위 선택

검증할 위험을 실제로 관찰할 수 있는 가장 작은 범위를 선택합니다. DB, 트랜잭션과 외부 프로토콜의 동작을 mock 호출 여부로 대체하지 않습니다.

외부 클라이언트의 실패 분류와 예외 변환은 예외 주입으로 검증하며, HTTP 서버는 요청 형식이나 응답 파싱 자체를 검증할 때 사용합니다.

| 검증할 위험 | 우선 선택 |
| --- | --- |
| 업무 정책, 계산, UseCase의 판단과 분기 | 단위 테스트 |
| 주요 업무 흐름 | 필요한 협력 범위를 포함한 단위 또는 통합 테스트 |
| 커밋, 롤백과 트랜잭션 전후의 부수 효과 | 실제 트랜잭션을 사용하는 통합 테스트 |
| SQL, 매핑, 제약조건과 쿼리 | PostgreSQL 컴포넌트 또는 통합 테스트 |
| 잠금, 동시성과 격리 수준 | 병렬 실행을 포함한 PostgreSQL 통합 테스트 |
| 외부 API의 프로토콜 매핑 | 클라이언트 계약 또는 컴포넌트 테스트 |
| 메시지 발행, 소비와 직렬화 | 브로커 계약 또는 컴포넌트 테스트 |
| HTTP 계약, 입력 검증, 인증과 오류 응답 | HTTP 컴포넌트 또는 통합 테스트 |
| 애플리케이션 연결과 핵심 사용자 시나리오 | 제한된 E2E 테스트 |

DB 동작은 운영과 같은 종류와 가능한 한 가까운 버전의 DB를 Testcontainers로 실행해 검증합니다. 인메모리 DB나 mock Repository로 SQL, 제약조건, 격리 수준이나 롤백을 증명하지 않습니다.

외부 저장소 실패로 DB 변경을 롤백해야 한다면 외부 경계에 실패를 주입하고, 실제 DB에 변경이 남지 않았는지 조회합니다. 호출 횟수나 테스트 이름만으로 롤백을 판단하지 않습니다. 외부 경계에 실패를 주입하는 테스트와 외부 프로토콜 자체를 검증하는 테스트는 구분합니다.

## 업무 규칙과 UseCase

업무 판단과 검증은 이를 소유한 UseCase에서 검증합니다. 반복되는 규칙을 Policy로 추출하면 해당 정책의 경계값과 거절 조건을 단위 테스트로 검증합니다. 규칙의 소유권은 [아키텍처](architecture.md#업무-규칙)를 따르며, 테스트를 위해 별도 도메인 모델이나 인터페이스를 만들지 않습니다.

업무 코드와 SQL 조건이 같은 규칙을 구현하면 동일한 경계값과 상태 조합을 양쪽에서 검증합니다. UseCase 테스트는 Policy에서 검증한 조합을 반복하지 않고 다음 결과를 확인합니다.

- 주요 업무 성공 흐름
- 데이터 접근과 업무 판단의 실행 순서에 따른 결과
- 같은 트랜잭션에서 커밋하거나 롤백하는 변경
- 트랜잭션 완료 전후의 부수 효과
- 실패 후 실행하지 않아야 하는 후속 작업
- 외부 실패가 실행 결과와 DB 상태에 미치는 영향

트랜잭션을 검증할 때는 Spring 프록시를 통과하는 실제 호출을 사용합니다. 테스트 전체를 트랜잭션으로 감싸 커밋과 롤백 결과를 가리지 않습니다.

## 이름과 구조

테스트는 Kotest의 `FunSpec`으로 작성합니다. `test("조건과 기대 결과")`에 한국어 이름을 작성하고, 영문 테스트 메서드나 `@DisplayName`을 별도로 두지 않습니다. DCI 구조나 `DescribeSpec`, `BehaviorSpec`은 사용하지 않습니다.

정책 단위 테스트의 가상 예시입니다.

```kotlin
class PasswordPolicyTest : FunSpec({
    test("최소 길이인 8자 비밀번호는 허용한다") {
        // given
        val password = "12345678"

        // when
        val result = PasswordPolicy().isValid(password)

        // then
        result shouldBe true
    }
})
```

테스트 이름과 주석의 업무 용어는 [용어집](../glossary.md)을 따릅니다.

테스트 이름은 구현 방식보다 조건과 관찰 가능한 업무 결과를 설명합니다. 관련 사례를 묶을 때만 `context("공유 조건")`를 사용하고, 모든 테스트를 형식적으로 중첩하지 않습니다.

새 정책이나 중요한 유스케이스의 테스트 이름은 다음 절차로 확정합니다.

1. 검증 대상, 실행 범위와 목적을 정리합니다.
2. 시나리오별 한국어 테스트 이름을 제안합니다.
3. 사용자가 시나리오와 이름을 검토하고 확정합니다.
4. 확정된 이름으로 테스트를 구현합니다.

사용자가 이름을 지정했거나 합의된 이름을 같은 의미로 적용하면 다시 확인하지 않습니다. 업무 의미를 유지한 채 기존 테스트 구현만 수정하는 경우에도 별도 확인을 요구하지 않습니다.

## Assertion

검증은 Kotest assertion을 사용합니다. 여러 검증이 하나의 결과를 설명하고 실패를 함께 확인해야 하면 `assertSoftly`로 묶습니다.

```kotlin
actual shouldBe expected
val value = result.shouldNotBeNull()
items shouldContainExactly expectedItems
```

예외는 `shouldThrow<예외타입>`으로 포착하고 메시지와 부수 효과를 검증합니다. AssertJ와 JUnit assertion을 혼용하지 않습니다.

## Given, When, Then

테스트 본문은 다음 순서로 작성하고 각 구간을 주석으로 표시합니다.

- `given`: 입력, 선행 상태와 협력자의 동작을 준비합니다.
- `when`: 검증 대상의 행위를 실행합니다.
- `then`: 반환값, 상태 변화, 저장 결과, 부수 효과나 실패를 관찰합니다.

중요한 입력과 기대 결과를 helper 안에 숨기지 않습니다. 예외도 실행 결과를 `when`에서 포착하고 `then`에서 예외와 부수 효과를 검증합니다. 하나의 업무 결과를 설명하는 assertion은 함께 두고, 독립적인 규칙은 테스트를 나눕니다.

## Fixture와 결과 관찰

- 결과에 영향을 주는 경계값, 상태, 시간과 식별자는 테스트 본문에 명시합니다.
- Instancio 같은 생성기를 사용한다면 시나리오와 무관한 유효한 기본값에만 사용합니다.
- 준비는 운영 코드의 기존 저장 기능을 우선 사용합니다. 필요한 기능이 없으면 테스트 클래스의 private helper에서 DB 상태를 준비합니다.
- 같은 준비가 여러 클래스에서 반복될 때 공유 fixture로 옮깁니다. 범용 builder, Repository 인터페이스나 컨테이너 추상화를 미리 만들지 않습니다.
- fixture에 업무 판단이나 assertion을 숨기지 않습니다. 테스트 편의를 위해 운영 API나 Repository 메서드를 추가하지 않습니다.
- 결과는 판단 로직을 다시 호출하지 않고 저장된 사실과 외부 응답으로 확인합니다.
- Repository의 기존 조회를 재사용할 수 있습니다. SQL이나 매핑 자체를 검증하거나 조회에 없는 컬럼을 확인하면 JDBC로 직접 관찰할 수 있습니다.

시간에 영향을 받는 테스트는 [시간 처리](../operations/time.md)의 `Clock` 기준을 따릅니다. JSON 필드 누락, 명시적인 `null`, 빈 문자열과 잘못된 타입은 구분하고 응답 상태, 오류 코드, 필드 오류와 부수 효과를 확인합니다.

## 통합 테스트 지원

단위 테스트는 Kotest의 `FunSpec`과 assertion을 사용하며 Spring 컨텍스트나 컨테이너를 실행하지 않습니다. 단위 테스트용 공통 부모 클래스는 만들지 않습니다.

테스트와 지원 코드는 Kotlin으로 작성합니다. 업무 통합 테스트는 [IntegrationTestSupport](../../src/test/kotlin/com/ject/support/IntegrationTestSupport.kt)를 상속합니다. support 클래스가 `FunSpec`, Kotest `SpringExtension`, `test` 프로필, Spring 컨텍스트와 PostgreSQL, Redis, S3Mock 컨테이너의 실행 및 접속 정보 주입을 담당합니다. Spring 확장은 통합 테스트 support에서 등록하고 단위 테스트에는 적용하지 않습니다.

support 클래스의 `jdbc`로 테스트 데이터를 준비하거나 저장 결과를 직접 조회할 수 있습니다. 테스트 클래스마다 `JdbcTemplate` 주입을 반복하지 않습니다.

컨테이너는 테스트 JVM에서 공유하며 support 클래스가 시작합니다. 테스트 클래스에 `@Testcontainers`나 `@Container`를 추가해 같은 컨테이너의 수명주기를 중복 관리하지 않습니다. 컨테이너 설정과 더미 값 관리 기준은 [환경 설정](../operations/configuration.md#환경별-값)을 따릅니다.

통합 테스트는 사용하는 자원과 관계없이 세 컨테이너를 함께 실행합니다. Redis와 S3 접속 정보를 테스트별로 등록하지 않습니다. Redis 키와 S3 객체 키는 테스트별로 구분하고 생성한 데이터를 직접 정리합니다. 공유 자원에 `FLUSHALL`을 실행하거나 버킷을 삭제하지 않습니다. S3 에뮬레이터는 Adobe S3Mock을 사용하며 서명과 만료 검증은 실제 OCI에서 수행합니다.

테스트는 실행 순서나 다른 테스트가 남긴 데이터에 의존하지 않도록 자신이 사용하는 데이터를 준비하고 정리합니다. 정리는 외래 키의 의존 순서를 따르며 업무 테이블과 무관한 스키마 이력은 삭제하지 않습니다. 공유 DB 데이터를 정리하는 통합 테스트는 병렬 실행하지 않습니다.

## 인프라, 공통 모듈과 설정

인프라 요소나 공통 모듈을 추가하거나 수정했다는 이유만으로 별도 테스트 코드를 작성하지 않습니다. 기동, 연결, Bean 구성이나 단순 위임만 확인하는 smoke test는 저장소에 남기지 않습니다. 기존 테스트도 이 확인만 수행한다면 삭제를 권장합니다.

작업 중 검증을 위해 임시 테스트를 작성할 수 있습니다. 검증이 통과하면 커밋 전에 임시 테스트와 해당 테스트만을 위한 fixture, 설정, 의존성을 삭제합니다. 임시 검증 코드는 Git에 커밋하거나 푸시하지 않습니다.

annotation 동작, 프로퍼티에 따른 Bean 활성화, Bean 종류와 개수, 필터 체인의 내부 구성처럼 프레임워크와 선언적 설정 자체를 확인하는 테스트는 추가하지 않습니다.

업무 결과, 실패 처리나 실제 결함의 재발을 검증하는 테스트는 인프라나 공통 모듈에 속하더라도 유지합니다. 트랜잭션 매니저의 종류 대신 실패 후 DB 상태를, 필터 목록 대신 요청의 허용과 거절 결과를 검증합니다. 프레임워크와 설정의 조합에서 결함이 재현되면 영향을 기준으로 회귀 테스트를 추가합니다. 기존 기능 테스트로 관찰할 수 없을 때만 근거를 남기고 내부 설정을 검증합니다.

설정 배치와 활성화는 [환경 설정](../operations/configuration.md)을 따릅니다. 예약 작업의 테스트 실행 기준도 같은 문서를 따릅니다.

## 작성 전 검토

- 검증 대상과 영향이 큰 실패를 실제로 관찰할 수 있습니까?
- 허용 조건, 거절 조건과 경계값이 드러납니까?
- 데이터 흐름, 트랜잭션 결과와 부수 효과의 순서를 확인합니까?
- mock 호출 검증이 실제 DB나 외부 프로토콜 검증을 대신하지 않습니까?
- 한국어 테스트 이름이 업무 보장을 설명하고 사용자 검토를 거쳤습니까?
- 본문에서 입력, 실행과 기대 결과를 찾을 수 있습니까?
- 테스트만을 위한 운영 코드 추상화를 추가하지 않았습니까?
